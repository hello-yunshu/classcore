## 二、R3.5专项审计问题的闭环情况

### 1. 缺少AGENTS/Codex交接入口 — 已闭环

根目录新增 `AGENTS.md` 与 `CODEX-HANDOFF.md`。新Codex不再依赖此前聊天才能理解Foundation冻结、Surface职责、D2/D7/D21、当前未完成项和下一步顺序。

### 2. README失效引用 — 已闭环

当前权威README和docs入口重新整理；`docs:check`通过。历史报告不再承担当前规则。

### 3. clean checkout直接npm test缺dist — 已闭环

`npm test -> npm run build -> test:unit`。构建产物不进入最终源码ZIP。旧Node运行该命令会先被runtime gate明确拒绝，而不是进入不可预测兼容模式。

### 4. Lesson Validator弱于正式Schema — 已闭环

通用`lesson:validate`执行正式Draft2020-12 Schema和跨文件校验，反例测试已证明非法Activity枚举不能再“假PASS”。

### 5. npm版本与Node官方基线冲突 — 已闭环

生产基线采用Node24.21.0 LTS及其npm11.19.0；不再为了npm单个patch制造首次bootstrap摩擦。

### 6. 缺package-lock — 已闭环到结构/流程层

R3.6包含lockfile，Docker/CI使用`npm ci`。当前沙箱做了workspace/lock结构检查与离线npm解析尝试，没有出现lock不同步错误；精确npm11在线`npm ci`仍必须在正式工具链环境跑一次Release Gate。

### 7. Docker下Backstage localhost逻辑冲突 — 已闭环

教师本机工具端口独立使用8788（Backstage + Authoring），Compose只映射宿主`127.0.0.1:8788`；课堂LAN端口8787只承载Student/Teacher/Display/Observer。Simulation不由生产Server暴露。权限边界由部署结构表达，不依赖容器内猜宿主IP。

### 8. 缺.env/example/bootstrap/doctor — 已闭环

全部存在，`server:dev`支持可选`.env`，bootstrap固定npm ci -> Python venv -> full check。

### 9. Foundation只靠人工“冻结” — 已闭环

46个Foundation文件建立hash基线；R3.5->R3.6实际0差异。

### 10. 缺最小CI — 已闭环

GitHub Actions最小CI使用Node24.21/npm11.19/Python3.13，npm ci后跑full check。不做无价值的大型matrix；`linux/amd64`多架构CI仍按D21推进。

### 11. formatter/linter — 辩证后部分闭环、暂不引入重依赖

加入`.editorconfig`和source quality check；不在真实UI尚未大量开发前引入Biome/ESLint依赖。后续只选一个工具，避免重复。

## 三、稳定性审计

当前reference server已经验证：

- Event/TeacherControl ID按Session隔离；
- serverSeq按Session持久化，重启后不倒退；
- duplicate retry返回原sequence，不二次推进；
- Stage只发同Session；
- Observer慢消费可丢Live，而Student durable/Teacher control保留；
- 单WebSocket消息有上限；
- 非hello连接不会提前进入正常消息链；
- public assets不再暴露整个dist；
- Backstage不走课堂LAN端口；
- SQLite/WAL真实close/reopen reference test通过。

这些更符合“稳定、流畅、可恢复”，而不是继续做复杂安全工程。

## 四、可维护性审计

### 当前可复用路径

新公开课默认：

`lesson:new -> Lesson Package -> Applet -> Analytics Profile -> Presentation -> Fixture/Simulation -> lesson:validate`

Foundation不应该随课程变化。

### 当前代码规模

Server vertical slice仍约数百行，已在`AGENTS.md`明确：不能继续演变成万能Server；新逻辑应逐步下沉到Runtime/Service/Adapter/Capability。

### 当前Design边界

前端视觉Design尚未冻结。中性Web Shell只保证路由和运行入口，未来单独开展Product Design/Design System，不让当前临时样式绑死产品。

## 五、跨架构审计

原则正确：

- 业务不按CPU分叉；
- 当前公开课P0：Apple Silicon + Docker `linux/arm64`；
- 长期兼容：`linux/amd64`；
- Browser按Capability，不按ARM/x86白名单；
- Dockerfile不强制amd64；
- current/multiarch build helper均从中央toolchain读取Node版本；
- TypeScript lock覆盖darwin-arm64、linux-arm64、linux-x64关键开发/构建目标。

## 六、工具链与“尽量新”的审计

最终原则不是“数字最大”，而是：**当前最新LTS/稳定线 + 精确可复现 + 易升级**。

当前：Node24.21 LTS / npm11.19 / TS7.0.2 stable。Node26仍作为未来LTS升级候选；升级通过中央配置和Release Gate，不维护Node22/TS5旧兼容分支。

## 十、最终建议

将R3.6作为Codex下一阶段唯一母版。新Codex解压后先读`AGENTS.md`与`CODEX-HANDOFF.md`，运行`doctor -> bootstrap`，随后直接进入Presentation Engine PoC与TransformBoard开发。

除非真实实现产生反例，不再进行R3.7式纯架构扩张。

## 十一、最终自我辩证审计补充（封包前）

### 1. Codex无缝接手是否真的成立

当前已具备根目录 `AGENTS.md`、`CODEX-HANDOFF.md`、精确工具链文件、lockfile、`.env.example`、doctor/bootstrap、正式Lesson Validator、Foundation防漂移、最小CI以及Apple Silicon Docker Gate。对于一个没有此前聊天上下文的新Codex，会有清晰的“先读什么、先跑什么、哪些不能改、下一步做什么”。

仍有两个外部环境Gate不能在本沙箱伪报完成：

- npm registry 安装链：当前沙箱网络安装尝试超时，因此 `npm ci` 的在线下载完整过程仍由CI/Codex联网环境首验；lockfile本身的workspace、version、resolved、integrity与TypeScript多平台条目已经静态验证；
- Apple Silicon Docker：当前沙箱没有Docker，也不是macOS arm64，因此 `npm run docker:gate` 必须在教师Mac上真实执行。

这两项都已经从“隐含知识”变成显式可执行Gate，不会要求下一位Codex重新猜步骤。

### 2. 是否应该继续增加依赖

本轮重新讨论了Biome/ESLint/Ajv等方案。结论是**暂不增加**。当前业务运行依赖几乎为零，TypeScript strict、正式Draft 2020-12验证、`.editorconfig`、source quality、56项自动测试和CI已经形成足够的开发约束。当前阶段增加更多开发依赖会扩大lockfile、bootstrap和跨架构验证面，而正式UI代码尚未进入规模开发。等Student/Teacher/Authoring Studio代码量明显增长后，再只选择一个formatter/linter。

### 3. 源码可维护性再次修订

封包前对72个TS/MJS文件做了语义不变的统一可读性整理，并为源码增加“单行超过360字符即失败”的反压规则，避免后续Codex再次生成高度压缩的一行式实现。整理后重新执行完整业务回归，56/56测试继续通过。Foundation文档未改。

### 4. 当前真正应该继续的工作

R3.6之后不再进行纯架构版本滚动。下一阶段应直接进入：Presentation Engine限时PoC、Authoring Studio Alpha、Student TransformBoard Practice Alpha、真实Join/Presence/Outbox/Submission链，以及Apple Silicon Docker/LAN/XP21A演练。只有真实实现产生无法由现有Foundation表达的反例时，才重新提出Foundation变更。
